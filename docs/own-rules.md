# Свои правила Last Edict (Э4)

Этап Э4 (`docs/own-version-roadmap.md` §3.2, §4): здесь правила игры впервые расходятся с оригиналом. Арбитр — снимки «порт против
порта» (`tests/snapshots`, `tests/Shared/PortSnapshot.cs`): каждая правка правил — осознанный diff снимков, объяснённый в коммите; правка
без правил снимков не меняет. Трасса снимков `D2_SNAPSHOTS_TRACE=<каталог>` пишет сохранение после каждого дня, журнал каждого боя и решения
ИИ по шагам — по ней разбирается любое расхождение хеша.

## 1. Ключ правил — id содержимого

Правила, состояние партии, сохранения и сценарии живут на id содержимого (`base:unit/knight`); id оригинала (`legacyId`) — только на входе
оригинала и в именах графики импорта. Подробно — `docs/content-schema.md` §2. Прокачанный юнит — тип и уровень (`UnitType.GrownLevel`), а не
вычисляемый `G000UG…`. Снимки изменились только хешами (трасса до и после совпала после перевода id во всех 167 файлах).

## 2. Раздельные генераторы

У оригинала один R250 на всё. В Last Edict у каждой системы свой поток от зерна партии (`RngStream`, `RngStreams.Derive`,
`GameSession.BattleRng`/`AiRng`/`LootRng`/`MapRng`):

| Поток | Что бросает |
|---|---|
| бой | `BattleSim` боёв карты, событий и экрана боя, повтор боя из журнала |
| ИИ | тактика, стратегия, найм лидеров, дипломатия, подарки и ответы, заклинания ИИ, вылазки воров ИИ |
| добыча | заклинания побеждённого |
| карта | события сценария, шпионы, действия воров человека, облик гор |

CRT `rand()` — поток процесса, как у оригинала (имена, фон боя, выбор найма ИИ). Таблица потока — SplitMix64 от пары «зерно, поток» с
диагональю Киркпатрика—Штолля (полный период R250). Зерно (`RandomReseed.Reseeded`) задаёт все потоки сразу: правка ИИ не трогает броски
боя — основа A/B баланса (`RandomReseedTests.Streams_AreIndependent`). Сохранение — версия 12: у старых единый поток становится потоком боя.

## 3. Инициатива на раунд вперёд (Р4, Р17)

- Случайная часть инициативы (`rng(BAT_INIT)`) раунда N+1 бросается в начале раунда N (`BattleSim.BeginRound`) и дальше не меняется. У
  первого раунда и у юнита без броска — бросок при построении; воскрешённым и призванным — в конце хода. Повторное построение раунда
  (раунд 1 строится дважды) бросков не тратит; бой кончился построением — следующий раунд не бросается.
- Порядок раунда считается по характеристикам на миг построения (`TurnOrder.Order`). Поэтому полоса следующего раунда
  (`BattleSim.NextRound`, `BattleSession.UpcomingNext`) живая: замедление, превращение, гибель, призыв, воскрешение двигают её сразу, а
  случайная часть неизменна. Конечное замедление, как у оригинала, гаснет при построении раунда.
- Текущий раунд идёт своим порядком: «Ждать» — в конец текущего раунда, дар атаки — сразу за ходящим.
- Полоса очереди (`BattleQueueStrip`) — два раунда (`BattleSession.TwoRounds`): следующий чуть темнее, перед ним золотая черта.
- Проверка: на боях test-pack очередь, предсказанная после последнего хода раунда, совпала с настоящей очередью следующего
  (`InitiativeAheadTests`, 13 боёв, 49 переходов раунда).
