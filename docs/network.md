# Сеть с друзьями (Э7)

Решения пользователя: Р5 (игра с друзьями, комната по коду), Р22 (посредник на дешёвом сервере, WebSocket; ИИ на свободных местах,
асинхронный режим, таймер хода по желанию хоста; ходы по очереди, как в оригинале), Р33 (людей одной партии — только по сети). Контракт
протокола — `docs/rust-web/03-contracts-and-multiplayer.md` (взят почти целиком), основа — команды и журнал (`docs/game-commands.md`).

Код: `src/Net` (`LastEdict.Net`, без Godot), посредник `tools/Relay`, игра — `godot/scenes/map/MapView.Net.cs`, `MapScreen.Net.cs`,
драйвер двух машин `tools/net-duo.py`.

## 1. Схема

Хост-сервер: игра хоста считает правила (настоящая `GameSession`) и раздаёт каждому человеку только его вид; посредник с кодом комнаты
пересылает сообщения между хостом и клиентами (порты у игроков не открываются). Хост в теории видит всё — между друзьями допустимо
(roadmap §3.5).

```
клиент (GameSession над видом) ──команда──▶ посредник ──▶ хост (GameSession партии) ── правила, ИИ, бои
          ▲                                      │                    │
          └──────── вид дельтой, ответ ◀─────────┴────────────────────┘
```

## 2. Вид игрока (`PlayerView`, `NetView`)

Проекция партии хоста для игрока — тоже `GameState`, поэтому окна, карта и бой клиента работают над ней как над обычной партией.
Разрешительным списком убирается:

- чужие отряды под туманом и невидимые — с юнитами, предметами, приказами; у видимого чужого отряда — сумка и приказы (снаряжение
  остаётся: оно в бою);
- содержимое объектов под туманом: владелец, гарнизон, стража, предметы, запасы лавок, деньги; мешки, жезлы и могилы под туманом;
  у городов и руин в облике — владелец и «разграблено»;
- у чужих игроков — казна, второй кошелёк, известные заклинания, постройки, разведка, обмены картами, туман (весь скрыт);
- генераторы случайных чисел, память стратегии и тактики ИИ, чужие предложения, попапы, итоги хода, записи квест-лога, наложенные
  заклинания и применения предметов, чужие убийства отрядов.

Остаётся известное и так: карта и постоянные объекты (сценарий есть у каждого, §7 контрактов), события сценария, дипломатия, игроки и
расы. Принятые утечки (между друзьями): счётчики id карты (нужны для id призванных в бою, иначе бой клиента разойдётся), переменные
событий, день последней постройки чужого игрока.

На проводе вид — JSON сохранения проекции (`GameSave`, время постоянное) плюс счётчики id (`NetView`: в сохранение они не пишутся).

## 3. Протокол (`Protocol.cs`)

Сообщения JSON с полем `$m`, порядковые номера — строкой:

| Сообщение | Кто | Что |
|---|---|---|
| `hello` | клиент | версия протокола и сборки, набор правил (`Ruleset`), имя, ключ места (возвращение), последний вид (эпоха, номер) |
| `welcome` / `refused` | хост | место (игрок партии) и ключ / отказ с кодом и текстом |
| `command` | клиент | `CommandId` (повтор — прежний ответ), `ExpectedViewSeq`, `TurnToken`, команда партии |
| `receipt` | хост | исполнена или отказ (`WrongTurn`, `StaleView`, `NotYours`, `InvalidCommand`, …), значение, отчёт, семя боя |
| `delta` / `snapshot` | хост | правки вида от номера к номеру (`ViewPatch`) с хешем / вид целиком с новой эпохой |
| `resync` | клиент | дельта не легла или хеш не сошёлся — нужен снимок |
| `turn` | хост | чей ход, право хода (только ему), день, срок таймера |
| `battleRequest` / `battleReply` | хост / клиент | бой хода ИИ с отрядом клиента: собрать у себя (отпечаток боя), сыграть, ответить действиями |
| `chat` | оба | строка игрока |

Дельта (`ViewPatch`) — правки по путям JSON: объекты — по полям вглубь, массивы одной длины — по элементам, разной — одной заменой
середины между общими началом и концом. Клиент накладывает её только на свой точный номер вида и сверяет SHA-256 каноничного вида;
не так — `resync`, не догадка. Длинные сообщения (снимок) сжимаются Brotli на проводе (`RelayLink`).

## 4. Хост (`NetHost`) и клиент (`NetClient`)

**Один обработчик на комнату.** Команды клиентов разбирает `Pump` на потоке хоста по одной: место и `command_id` → право хода, номер вида
→ права на объекты (`CommandRights`: свои отряды, крепости, игрок; нападение — только на цель на виду; конец боя — только своего
открытого и только действиями) → исполнение (сбой — откат партии, генераторов и боя, `GameSession.Checkpoint/Restore`) → рассылка
видов → ответ → смена хода. Свои команды хоста (его окна) идут тем же путём (`GameSession.Remote`), после каждой клиенты получают вид.
Замки: исполнение партии (`_gate`, весь ход ИИ) и места (`_seatsLock`) — уход соединения и ответ на бой хода ИИ не ждут исполнения.

**Команды клиента** (`GameSession.Remote` → `NetClient.Run`) уходят хосту, клиент ждёт ответа; вид меняют дельты (в игре — на потоке
показа, `NetSession.Pump`). Не в свой ход клиент команд не шлёт — кроме снятия своих показанных попапов (`takeMessages`).

**Бой — у клиента, хост проверяет** (решение пользователя 25.10): бой своего экрана клиент собирает у себя по виду (`startBattle`,
`endBattle` исполняются и у него), генератор боя и CRT — копия хоста (семя в ответе на `startBattle`); хост повторяет бой по действиям
(`BattlesPlayedElsewhere`) и сверяет журнал ходов — итог хоста. Удары без задержки на сеть; цена — клиент знает броски этого боя.
Бой хода ИИ с отрядом клиента: хост шлёт `battleRequest` (группы, отпечаток боя, семя), клиент собирает тот же бой по виду
(`BuildBattleHere`, отпечаток `BattleFingerprint`), играет экраном и отвечает действиями; хост повторяет; нет ответа или бой не
собрался (нападающий невидим) — автобой. Журнал хоста пишет такой бой решением снаружи — повтор сходится.
Бой события в сети — автобой у всех (настройка `EventBattlesOnScreen` одна на журнал).

**Бой двух людей — «каждый своих»** (решение пользователя 25.10). Оба экрана ведут один бой: одно состояние, копии одного генератора
боя и CRT (`BattleSetup.BothHuman`). Записывает бой тот, кто начал (`startBattle`), — его `endBattle` и есть итог; другой получает
`battleRequest` с `Lockstep` (бой у хоста — сразу `LockstepRequested`). Каждое своё решение (удар, защита, ожидание, отступление,
предмет) экран отдаёт событием `BattleSession.Recorded`, оно идёт `battleStep` через хоста другой стороне и исполняется там тем же
путём, что щелчок (`BattleScreen.Net.cs`, с показом); решения, пришедшие раньше, чем открылся экран, ждут его (`MapScreen._netSteps`),
чужие и не к этому бою — мимо, шаг принимается только от стороны боя. Начало хода и ходы ИИ каждый экран считает сам — они
детерминированы. «Быстрый бой» и автобой стороны выключены (миг у экранов разный). Автобой решает только записывающий экран: другая
сторона молчит 90 с (нет связи) — её юниты ведёт ИИ, срок хода вышел — автобой всего боя; это тоже шаги (`setAuto`, `playOut`), второй
экран повторяет их, и бой у обоих тот же. Второй экран ждёт записывающего 180 с, его бой — только показ: итог — `endBattle`
записывающего, хост повторяет его по действиям. Место и фон экрана — по виду на миг сборки боя (вид мог уйти вперёд).

**Ход и таймер.** Ходы по очереди дня, как в оригинале (`GameSession.DayOrder`): ИИ ходит между людьми у хоста. Право хода — токен,
выданный тому, чей ход. Таймер хоста: клиент в срок заканчивает ход сам (открытый бой — автобоем), не закончил (нет связи) — хост с
запасом 10 с заканчивает за него.

**Переподключение.** Клиент возвращается по ключу места с последней эпохой и номером вида: хост дошлёт недостающие дельты (последние 64)
или снимок новой эпохи. `RelayLink` переподключается сам (1, 2, 4 … 15 с). Обрыв посреди команды — отказ «нет связи», окно не виснет.

## 5. Набор правил (`RulesetHash`)

Один на игру, сеть и `d2mod pack` (договор со «Студией 2»). Хеш (полный SHA-256): база содержимого (файлы видов) и моды по порядку
наложения; у мода — `mod.json` (id, `dependencies`, `loadAfter`), файлы видов, `entity.json` «папок = сущностей», `plugins/*.dll`. Не
входят строки, значки и картинки (`*.png` в `content/`), графика, звук, разметка, сценарии; мод без файлов правил (HD-слой) в набор не
входит вовсе. JSON — каноничный. Разные наборы — отказ входа с текстом: «нет мода …», «лишний мод …», «мод … другой версии», «другая база
содержимого». Мод, который исполняет код, входит в набор плагином: у всех тот же — значит, разрешён у всех.

## 6. Посредник (`tools/Relay`)

ASP.NET Core, WebSocket `/ws`, `/health`; правил не знает, сообщения игры — непрозрачные строки. Комната — код из 6 знаков (31 знак, без
похожих), участник — номер и ключ (хранится хеш), место в партии уникально и при возвращении не меняется. Лимиты: сообщение 16 МБ,
попытки входа и создания с адреса — 30 в минуту, кадры — 100 в секунду (запас 400), очередь отправки — 96 МБ (медленный получатель
закрывается), участников — 16, журнал асинхронной комнаты — 64 МБ, пустая комната живёт 30 минут, асинхронная без ходов — 60 дней.
Остановка закрывает соединения сразу (клиенты переподключатся). Переменные: `ASPNETCORE_URLS`, `RELAY_DATA`, `RELAY_PATH_BASE`,
`RELAY_TRUST_PROXY=1` (адрес — из `X-Real-IP`). Секретов нет. Образ — `tools/Relay/Dockerfile`.

## 7. Игра

Чужой ход — тот же режим, что ход ИИ: ввод заперт, окно ожидания, рабочий поток ждёт своего хода (`MapView.WaitOthers`). У хоста он же
исполняет конец хода клиента — ходы ИИ показываются как свои, бой ИИ с человеком хоста — его экраном; у клиента показывает бои хода ИИ,
о которых просит хост. Пока ждёт — карта по новой партии без анимации. Экран боя ИИ в сети — только со своим отрядом. Автосохранений
одиночной игры в сети нет. Сетевая партия начинается с записанного и прочитанного состояния (`NetGames.NewGame`) — как асинхронная.

**Лобби «Мультиплеер»** (главное меню → `LE_LOBBY`, модель `LobbyLogic`, окно `godot/scenes/net/LobbyWindow.cs`). Адрес посредника и
имя; адреса в игре и репозитории нет — переменная `LE_RELAY` или последний введённый (`user://net.json`, `NetPrefs`). «Создать»:
сценарий (с двумя расами и больше), места — я / друг / ИИ (`CycleSeat`), таймер хода, асинхронная партия; набор правил
(`RulesetHash`, моды по порядку) — свой. Комната с кодом; «Начать» — когда вошёл хоть один друг: места друзей по порядку входа, не
пришедшие — ИИ. «Войти»: код → свободное место
(`ClaimSeatAsync`, у посредника — операция `seat`, место одно на участника); набор правил не тот — отказ с текстом. Свои комнаты —
`user://net-rooms.json` (`NetRooms`): асинхронную партию открывают из списка, «ваш ход» — там же.

## 8. Асинхронный режим (`AsyncRoom`)

Сходил — закрыл игру — друг ходит позже. Партию целиком хранит посредник; тот, чей ход, берёт её (хеш сверяется), ходит у себя (ходы ИИ
после него — у него же), записывает следующей ревизией с журналом хода и тем, чей ход дальше. Писать может только тот, чей ход, и
только следующей ревизией. «Ваш ход» — сразу, если на связи, иначе — в списке комнат меню (уведомление — в игре, решение 25.10).
Партия ходящего — полная (показ — по его туману). Бой хода ИИ с отсутствующим человеком — автобой. Хеш записи — хеш того, что прочтёт
следующий: чтение сохранения упорядочивает известные заклинания (как движок при загрузке), поэтому асинхронная партия — партия с чтением
между ходами, и повтор (`AsyncRoom.ReplayTurns`) повторяет журналы ходов так же. Пока ход пишется, партия у посредника не берётся
(ответ на опрос мог уйти раньше записи), и ход с ревизией не новее своей записи — не свой. Ответ на запись пропал, а посредник её
принял — повтор получает отказ ревизии, читает партию и, если там уже эта (ревизия и хеш), считает ход записанным; 10 неудач подряд —
сообщение игроку. Запросы к посреднику у соединения — по одному (`RelayLink.Request`): ответы у посредника без номера запроса.

- `py tools/net-duo.py [--case play|drop|async|duel] [--days N] [--remote] [--relay URL]` — две игры через посредника (на ПК или
  ПК + EliteBook), ходы по сценарию (`ScriptedHuman`; `duel` — бой людей: перед началом отряд гостя ставится рядом с большим отрядом
  хоста `--net-meet`, хост стоит `--net-hold`, гость нападает — записывает он, защитники хоста ходят решениями по сети), сверка хеша хоста и вида
  клиента с повтором журнала (`tools/JournalReplay --view`, асинхронная — `--async`). Итог — задержка команды, трафик, память.

## 10. Развёртывание

Посредник — контейнер из `tools/Relay/Dockerfile` (`docker build`, `docker run -p 8790:8790 -v <том>:/data --memory 256m --cpus 0.5
--restart unless-stopped`), куча .NET ограничена 160 МБ. Свой порт наружу, без чужого nginx (решение 25.10); за обратным прокси —
`RELAY_PATH_BASE` и `RELAY_TRUST_PROXY=1`. Адрес сервера не публикуется: игрокам его сообщают сами.
